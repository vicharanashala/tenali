## 1. What is Tenali?

Tenali is a web app where school students practise maths by playing. It is named after Tenali Raman, the court poet known for solving problems with wit, and the tone of the app follows that: puzzles, games, a mascot, coins and badges instead of worksheets.

The main users are school children, roughly from early arithmetic up to calculus, practising on their own. Teachers and admins come second, through the proctoring and progress tools.

The problem it addresses is simple to state. A child who is practising needs a steady supply of questions at the right level, and fixed question banks run out or stay at one level. Tenali does not store questions. Each one is generated by the server when it is asked for, from a difficulty level, so practice never runs out. The difficulty moves up and down with how the child is doing, so they stay at a level that is hard but possible.

Around that core sit the things that keep a child coming back: coins and hints, a guided learning journey, daily warm-ups, Misconception Monsters for repeated mistakes, the Battle Arena, the detective stories and the Vachana literacy lab. Overall, Tenali is meant to be an endless, adaptive practice partner that a child actually wants to open.

## 2. What do you understand by Tenali (as a system)?

I understand Tenali as **one Node/Express server that generates and checks questions, and one large React app that turns those questions into games**, plus MongoDB for anything that has to be remembered about a student.

**Users**

- **Students.** They can use most of the app without an account (guest mode). With an account, their progress, coins and mastery are stored.
- **Admins / proctors.** Users with `role: 'admin'` in their JWT. `requireAdmin` in `server/auth.js:334` protects the admin and proctoring routes.

**Main entities**

- **Puzzle type.** The basic unit. Each type is an API prefix such as `/addition-api` with `GET /question` (generate) and `POST /check` (grade). `server/index.js` mounts **93** of these `*-api` prefixes (lines 163 to 1226 at `dc9f17a5`, which is also current `main`). Most of them point at routers in `server/routes/` (19 files), for example `app.use('/addition-api', arithmeticRouter)` at `server/index.js:567`.
- **Topic and prerequisite graph.** 69 topics with "this needs that" edges. This drives the `/graph` and `/path` pages and the Learning Journey order.
- **Student records** in MongoDB: `User`, `Progress`, `UserStats`, `UserTopicProgress` and others in `server/auth.js`, plus `Attempt`, `ConceptMastery` and `LearningEvent` in `server/lil/models.js`.
- **Learning Journey.** A sequenced route through topics with checkpoints (`/api/learning-journey/*`, `server/index.js:1134-1206`, data in `server/lil/learning_journey/`).

**How a normal practice session flows**

1. The student picks a tile on the home grid. `client/src/App.jsx` keeps the current screen in a `mode` state (there is no router), and `modeMap` maps that string to a component.
2. Most quiz screens come from the `makeQuizApp` factory in `App.jsx`. It calls `GET /<type>-api/question?difficulty=N`. In development `client/vite.config.js` proxies these paths to the server on port 4000; in production Express serves the built client itself.
3. The answer is sent to `POST /<type>-api/check`. If the student presses **Solve**, the solve middleware adds a step-by-step explanation to the same response.
4. The client moves its adaptive score up or down and asks for the next question at the new difficulty.
5. For signed-in students, progress is saved through `/api/progress`. Separately, a middleware in `server/index.js` passes every `*-api/check` answer (and Concept Playground attempts) through `server/lil/processAttempt.js` into `masteryEngine.js`, which writes `ConceptMastery` under the API path name (e.g. `addition`).

**How the parts connect**

The server is close to stateless for questions. Everything about the current question lives in the browser. Only progress and mastery are stored. Auth is a JWT in `localStorage` that the client sends as a Bearer token. Real-time Battle Arena uses Socket.IO from the same Express process. One Node process serves the API, the built React app, the `/graph` pages and the sockets.

## 3. Current State of the Repository: What Has Been Done So Far

**Technology stack**

- Client: React 19 (`client/package.json`: `react ^19.2.4`), Vite 8, ESLint 9, Socket.IO client.
- Server: Express 5 (`^5.1.0`), Mongoose 9 (`^9.6.1`), `jsonwebtoken`, `bcryptjs`, Socket.IO 4. Vitest 4 and Supertest are in `server/package.json` for tests.

**Architecture**

- `client/src/App.jsx` is a single file of **71,159 lines**. It holds `App`, `makeQuizApp`, `modeMap`, the home screen and most quiz components. Some apps have been split into their own files (`LcmHcfApp.jsx`, `BattleApp.jsx`, `PercentExplanationApp.jsx`, `client/src/monsters/`, `client/src/vachana/`, `client/src/proctor/`, `client/src/components/LandingPage/`).

- The prerequisite graph exists as three copies: `graph/index.html`, `graph/path.html` and `client/src/lib/prerequisiteGraph.js` (see 4.2).

**Authentication and authorisation**

- `server/auth.js`: JWT with a 14-day default TTL (`JWT_TTL`, line 29), bcrypt with 10 rounds (line 282), and `requireAuth` / `requireAdmin` middleware (lines 321 and 334).
- It refuses to start in production with the default secret (lines 34-37) and warns in development.
- If MongoDB is down, the users listed in `TENALI_SEED_USERS` can still log in from an in-memory map (`inMemoryUsers`, line 278).

**Frontend structure and UI**

- No router. Navigation is `setMode(...)` plus `history.replaceState` to keep `?mode=` in the URL.
- A newer landing page (`components/LandingPage/`) with a top navbar, then a puzzles grid driven by the tile registry.
- Many topics now open on a "Learn / Test" chooser before the quiz (in `App.jsx`, the `learningPhase === 'select'` screen).
- Global styles live in `client/src/App.css`. Theme switching uses CSS variables (`--clr-*`), with dark and light palettes.

**APIs and services**

- About 93 puzzle APIs (`/<type>-api/question` and `/check`).
- `/api/auth`, `/api/progress`, `/api/hints`, `/api/translate`, `/api/review` (daily warm-up), `/api/concept-session` (Concept Playgrounds) and `/api/learning-journey/*`.
- The proctoring routes, Socket.IO for battles, and the multi-language code playground.

**Database design**

- MongoDB through Mongoose.
- `server/lil/models.js` defines `Attempt`, `ConceptMastery` (unique on `userId + topicId`, line 41) and `LearningEvent`.
- `server/auth.js` defines the user, progress, stats and milestone models.

**Existing modules**

Adaptive quizzes, Solve explanations, hints with coins (`components/HintSystem/`), Learning Journey with checkpoints, Concept Playgrounds, Daily Spaced Review, Misconception Monsters, Battle Arena, Vachana, the Detective Agency, the GeoCraft and Visual Learning labs, and the `/graph` and `/path` prerequisite pages.

**Deployment**

- Production runs as a systemd service behind Nginx on `tenali.fun` (described in `DEPLOYMENT.md`).
- `.github/workflows/deploy.yml` deploys over SSH.
- `render.yaml` is kept for Render (`startCommand: node server/index.js`, health check `/api/health`).
- `docker-compose.override.yml` and `setup_mongo.sh` exist for local MongoDB.

**Testing and CI**

- `.github/workflows/test.yml` runs three jobs:
  - BKT unit tests (`node server/lib/bkt.test.js`),
  - client lint (marked `continue-on-error: true`, line 44),
  - server tests with a MongoDB service.

- There is no client test job (see 4.4).
- Other workflows: `pr-gate-check.yml` (Parikshak, which checks for a linked issue, merge conflicts and lockfile removals), `label.yml`, `parikshak-stale-check.yml` and `update-readme.yml`.

## 4. Gaps Observed in the Code

Every item below is something I either read in the code or ran into while working on the repository. Line numbers are from `main` at `f6df9ab0`.

### 4.1 Topic mastery is written but nothing reads it back, and the rule is very loose

- **Where:**
  - `server/lil/masteryEngine.js:12-42`, which writes `ConceptMastery`.
  - `server/lil/models.js:31-43`, the schema.
  - Searching the code for `api/mastery` finds no route.
- **What:**
  - Mastery is stored for each student and topic, but there is no endpoint that returns it, so no screen can show a student what they have mastered.
  - The rule itself (lines 24-31, commented "Standard baseline mastery rule: mark completed on correct answer") marks a topic as mastered after **one** correct answer. Three wrong answers in a row un-master it.
- **Why it matters:**
  - Everything that wants to personalise the app (a progress map, "what to learn next", unlock counts) has no data to work with.
  - Once it is exposed, "one correct answer = mastered" will overstate how much a child knows. Issue #289 tracks wiring BKT into `masteryEngine` for this reason.

### 4.2 The prerequisite graph is copied in three places

- **Where:**
  - `graph/index.html` (`const nodes` at line 97, `const edges` at line 192),
  - `graph/path.html` (lines 247 and 319),
  - `client/src/lib/prerequisiteGraph.js` (lines 7 and 96).

  Each copy has 69 nodes.
- **What:** The same graph is hand-maintained three times. I diffed them and they currently match, but nothing checks that they stay in sync.
- **Why it matters:** Someone adding a topic or an edge in one file will silently leave the `/graph` page, the `/path` page and the React app disagreeing about what a topic needs. This is the same kind of drift that issue #233 wants a CI check for.

### 4.3 The engagement-event model exists, but the UI has no way to record anything

- **Where:**
  - `server/lil/models.js` (`LearningEvent`),
  - `server/lil/eventGenerator.js`.

  The only caller of `eventGenerator.emit` is `server/lil/processAttempt.js:76`.
- **What:** `LearningEvent` is only written for `mastery_unlocked`. There is no route a client can use to record that a student opened a feature, followed a link or finished a step.
- **Why it matters:** There is no way to tell whether new features are actually used. That makes it hard to decide what to improve or remove.

### 4.4 Client tests cannot run, and CI does not try

- **Where:**
  - `client/package.json` scripts (only `dev`, `build`, `lint`, `preview`),
  - `client/vitest.config.js` (sets `environment: 'jsdom'`),
  - `.github/workflows/test.yml` (no client test job).
- **What:**
  - `vitest` is not a client dependency and there is no `test` script, so files like `client/src/detective.test.jsx` never run.
  - The config is there but nothing uses it.
- **Why it matters:** Client logic (adaptive difficulty, scoring, UI state) has no automated safety net. Issues #229 and #294 cover this.

### 4.5 Client lint is non-blocking and main carries 220 errors

- **Where:**
  - `.github/workflows/test.yml:29-44` (`continue-on-error: true`),
  - `client/src/App.jsx`.
- **What:**
  - Running `npx eslint .` in `client/` on main gives **220 errors and 126 warnings**, nearly all in `App.jsx`.
  - Some are real bugs, not style: issue #256 lists 24 `no-undef` errors in `App.jsx`, "at least one is a real ReferenceError".
- **Why it matters:** A permanently red, non-blocking check stops anyone noticing new errors. A contributor can add a real bug and CI still passes.

### 4.6 One global `button` rule styles every button in the app

- **Where:** `client/src/App.css:389-437` (`button`, `button:hover`, `button:disabled`).
- **What:**
  - Every `<button>` gets `padding: 12px 28px`, an orange background, a darker orange on hover and `opacity: 0.4` when disabled.
  - Any component that uses buttons as cards, chips or icons has to override each of these one by one.
- **Why it matters:**
  - I ran into this directly. Round icon buttons rendered as stretched pills.
  - A disabled answer button, which was meant to show the correct answer after a reveal, faded to 40% and became hard to read.
  - It makes every new component fight the stylesheet.

### 4.7 The floating coin badge covers page content on phones

- **Where:** `client/src/components/HintSystem/HintModal.jsx:688` (`position: 'fixed', top: '64px', left: '16px', zIndex: 10000`).
- **What:** The coin balance is pinned at the same spot on every screen, above almost everything. Screens are not designed around it.
- **Why it matters:**
  - At phone widths it sits on top of the "← Home" button on quiz screens.
  - On a full-screen map page I built, it covered the progress text until I moved the page above it.
  - A child can lose the way back out of a screen.

### 4.8 The landing page requests a video that is not in the repository

- **Where:**
  - `client/src/components/LandingPage/AppVideoDemo.jsx:20` (`fetch('/demo.mp4', { method: 'HEAD' })`),
  - line 120 (`<source src="/demo.mp4">`).
  - There is no `demo.mp4` under `client/public/`.
- **What:** Every visit to the landing page makes a request that fails.
- **Why it matters:** It shows as an error in the browser console on the first page every visitor sees. That hides real errors during testing and wastes a request on mobile data.

### 4.9 Start screens use fixed padding that cramps phones

- **Where:** `client/src/App.jsx:41750`, `48582` and `49200` (`padding: '48px 40px'` on the start cards).
- **What:** 40px of side padding is used at every screen width.
- **Why it matters:** On a 390px phone, content inside these cards ends up around 170-200px wide. Anything placed in them is squeezed, which I saw with an explanation panel on the Addition start screen.

### 4.10 `server/node_modules` is committed

- **Where:** `git ls-tree -r upstream/main server/node_modules` lists **591** tracked files.
- **What:** Dependencies are checked into git.
- **Why it matters:**
  - Running `npm ci` in `server/` (as `CONTRIBUTING.md` asks) modifies tracked files. That happened to me, and those changes nearly went into my PR.
  - It also bloats the repository and makes dependency changes hard to review.

## 5. Ideas for the Project

### 5.1 Expose mastery honestly, then make it stricter (from 4.1)

- **What:** A read-only `GET /api/mastery`. It returns the student's mastered topics, and a 503 (not an empty list) when the database is unavailable.
- **Why:** Personalised screens need this data. Returning "nothing mastered" on an error would show a returning student zero progress as if it were real. `CONTRIBUTING.md` already treats that as an automatic finding.
- **How:**
  - A small router using `requireAuth` that reads `ConceptMastery`.
  - The client treats signed-out as "unknown" and a failed request as an error state, never as an empty set.
  - Later, swap the one-correct-answer rule for the BKT estimate (issue #289), without changing the endpoint.

### 5.2 One source for the prerequisite graph (from 4.2)

- **What:** Treat `graph/graph-data.json` as the single source (it already is for the `/graph` and `/path` pages and `PathMap`), and add a test that fails if the client copy in `prerequisiteGraph.js` drifts from it.
- **Why:** The two HTML copies are already gone. The last hand-edited copy is the client module, and nothing catches drift there.
- **How:**
  - A Vitest test compares ids and edges in `client/src/lib/prerequisiteGraph.js` with `graph/graph-data.json`, and checks for duplicate edges and cycles.
  - A later step could have the client import `graph-data.json` directly, so there is nothing left to compare.

### 5.3 A safe engagement-event endpoint (from 4.3)

- **What:** `POST /api/events` that writes through the existing `eventGenerator.emit`.
- **Why:** It shows whether features are used, without building a new analytics system.
- **How:**
  - Use `requireAuth`, and never fail the user's action if logging fails.
  - Validate input before it reaches MongoDB: snake_case event names, short topic ids, and a plain-object payload under 2 KB.

### 5.4 Turn on client tests (from 4.4)

- **What:** Add `vitest` as a client dev dependency, a `test` script, and a `client-test` job in `test.yml`.
- **Why:** Client logic gets the same safety net as the server.
- **How:** Start with tests for pure logic that need no DOM (data files, state helpers). Make the job blocking, and add DOM tests once `jsdom` is set up.

### 5.5 Scope the global button style (from 4.6)

- **What:** Move the orange "primary button" look from the bare `button` selector to a class (`.btn-primary`), step by step.
- **Why:** New components would stop needing a long list of overrides, and disabled buttons would not fade by default.
- **How:**
  - Add the class.
  - Apply it to existing call sites screen by screen (the quiz factory first, since it covers ~45 screens).
  - Only then narrow the global rule.
  - Check each step with screenshots.

### 5.6 Give the floating chrome a home (from 4.7)

- **What:** Move the coin balance into the top navbar / app shell instead of a fixed badge. Until then, have full-screen tools sit above it.
- **Why:** Nothing would ever cover a back button again.
- **How:** Render the balance next to the existing navbar controls. Keep the fixed badge only on screens without the navbar.

### 5.7 Smaller fixes

- **From 4.8:** Either add the demo video to `client/public/` or render the fallback without requesting it.
- **From 4.9:** Make the start-card padding responsive (`clamp(16px, 5vw, 40px)`).
- **From 4.10:** Remove `server/node_modules` from git and add it to `.gitignore`.

### 5.8 Product idea: tell children *why*, and help them focus

These came from using the app as a student would, alongside the code reading above.

- **Nothing on a topic says why it matters or what it leads to.** The prerequisite graph already knows what each topic builds on, but the student never sees it.
- **The puzzles screen is busy.** It shows 100+ tiles (the tile registry in `client/src/features/tiles.js`, see `README.md:128`), banners and side games. That suits exploring, but a student revising three topics for an exam gets pulled away.

My proposals:

- **A "Why learn this?" panel** on each topic: a short, child-friendly reason, a small interactive demo, the steps of the method, and "learn these first / leads to" links built from the graph.
- **A "Why Mathematics?" guess-first activity** on the home screen.
- **An "Explore" view inside the existing Learning Path (`PathMap`)**: the whole topic graph on one screen, with real mastery when signed in. It reuses PathMap's goal path rather than adding a second map.
- **A Focus Mode** that hides everything except the topics a student picks, with a study timer.

All four are built on data and models that already exist (4.1-4.3), not on new back-end systems.
