- **Feature Name**: Prerequisite Auto-Routing & Warmups
- **Target SRS ID**: `Feature P`
- **Author**: Priyanshu Kumar (@priyanshu7725)

## Feature Description
This feature introduces an active safety routing engine to implement mastery learning. Instead of permitting students to fail repeatedly or artificially reducing problem difficulty, the system identifies when a student is struggling. It intercepts the active quiz, identifies likely prerequisite concepts that may be contributing to the student's difficulty, and routes the student to a quick, targeted warmup on that prerequisite before seamlessly returning them to the original workflow.

## Final Architecture (v1.0)
- **Direct Prerequisite Lookup**: Fetches prerequisite dependencies directly from the server adjacency list configuration (`prerequisites.json`) via dynamic endpoint lookups.
- **Student-Controlled Prerequisite Selection**: Employs the Prerequisite Picker UI modal, letting users select a supported prerequisite or continue with their active task.
- **Warmup Compatibility Whitelist**: Ensures fetched prerequisite topics pass compatibility checks (single text/numeric input and matching `/check` structure). Uses `getWarmupPrompt` to normalize diverse question shapes.
- **Progressive Intervention**: Escalates struggle triggers progressively (Auto-Warmup → Prerequisite Picker → Learning Recommendation).
- **State Preservation and Seamless Return**: Preserves quiz context (`frozenQuizState`), restores state cleanly, and triggers dual cooldown filters (`cooldownRef = 4`, `hesitationCooldownRef = 2`) to ensure smooth return paths.
- **Failure Mode Fallback**: On prereq fetch failure, retries once after 1s, then falls back to the v0.1 hardcoded warmup (`WARMUP_QUESTIONS_V01`). Chain-through-parents (Q10b) was deferred to v1.1.
- **Suffix Normalization at Hook Boundary**: Server endpoints use `-api` suffix (e.g., `addition-api/question`) but the prereq graph uses bare keys (`addition`). The hook strips `-api` for prereq lookups and appends it for `/question` and `/check` calls. Fixed in v1.0 after backend audit revealed the inconsistency.

- Telemetry cleanup

## Final Design Philosophy
Feature P evolved from an automatic prerequisite routing system into a student-guided intervention framework. Rather than assuming the system can precisely infer a student's knowledge gap, the final design combines automated struggle detection with student choice, allowing learners to decide which prerequisite concept they wish to review while preserving quiz progress and minimizing frustration.

## Hesitation Threshold Tuning
The Hesitation Monitor originally required 3 input clears per question to trigger. v1.0 lowered this to 2 clears after user testing revealed the 3-clear threshold was too conservative. Detection also works for NumPad-driven clears (added in commit `1a31097` — original implementation only fired on keyboard-driven DOM `input` events, missing NumPad clicks which don't dispatch native input events). Threshold and idle timer both live in `useWarmupIntervention.jsx`.

## v1.0 Scope and Limitations
**Shipped (14 single-input topics)**: basicarith, multiply, sqrt, quadratic, funceval, indices, addition, squaring, lineareq, rounding, ratio, percent, decimals, sequences.

**Actually wired with warmup working (11 modules)**: basicarith, multiply, sqrt, quadratic, funceval, indices, addition, squaring, ratio, percent, sequences. (Plus MCQ variants gk, dotprod, makeMCQuizApp — pre-wired by gemini-era code, not Feature P work.)

**Ship without warmup by design (v1.0 user decision B)**: lineareq, rounding, decimals — built via `makeQuizApp` factory. Factory migration deferred to v1.1.

**Completed warmups are re-clickable by design**: When a student completes a warmup on a prereq, the Picker still shows that topic with a ✓ indicator and an enabled button. This is intentional — students may want to revisit material they partially missed. The `sessionWarmupTopicsRef` is used only for the ✓ visual marker, not to disable the button.

**Deferred to v1.1**:
- 6 multi-input topics need server-side adapters (lineq, polymul, polyfactor, primefactor, qformula, simul)
- `makeQuizApp` factory migration (~46 call sites)
- RandomMixApp + CustomApp full hook integration
- Chain-through-parents failure mode (Q10b)
- 47 missing topic routes (topics in prereq graph without server endpoints: trig, integ, diff, vectors, etc.)

### Manual Verification Steps
- Step 1: Initiate a complex module (e.g., Quadratic Evaluation).
- Step 2: Submit three (3) incorrect answers out of four consecutive answers.
- Step 3: Validate that the Tier 1 Auto-Warmup launches and recommends the correct prerequisite.
- Step 4: Select "Take Warmup", submit three (3) correct answers within the warmup interface, and validate that the application automatically restores the state and routes back to the Quadratic Evaluation module.
- Step 5: Complete a warmup, return to the quiz, and verify that the Hesitation Monitor remains suppressed for the next two submitted questions before automatically re-enabling.
- Step 6: Trigger the Hesitation Monitor by clearing input fields 2+ times within a single question (or remaining idle for 60 seconds — see `useWarmupIntervention.jsx:resetTimer`), verifying that the soft intervention suggestions appear.

## Acceptance Criteria
- Sliding window correctly flags poor performance (3/4 wrong).
- Picker options correctly disable unsupported formats with a `[Practice coming soon]` tag.
- Completed topics remain selectable to permit student optional practice (tracked via `sessionWarmupTopicsRef` Set; the ✓ indicator marks them in the Picker but the button stays enabled so students can re-practice a warmup if they want to revisit material).
- Completed warmups bypass struggle-trigger loops for subsequent questions via cooldown guards.
- The system avoids repeatedly recommending the same prerequisite warmup within a single quiz session.
- Database starts without connection crashes.

## Appendix: Implementation Notes
- **Local DB Connection Timeout**: During integration testing, we resolved a startup database connection crash by increasing Mongoose `serverSelectionTimeoutMS` from 4000 to 10000 inside `server/auth.js`. This prevents connection timeouts caused by the synchronous `bcryptjs` password hashing routine blocking the Node.js event loop during startup.
